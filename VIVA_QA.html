Guri Finance — Code Defence Viva Question Bank

Microservices-based Finance Tool for Kosovo. Questions are ordered from most likely to least likely to be asked. Each answer is written so you can defend a real design choice honestly — where the code has a known weakness, the answer names it and gives the production-grade fix, which is exactly what examiners reward.

How to use this document

Read top-to-bottom at least once. The early tiers (project framing, architecture, the event/saga flow, accounting correctness, and security) are where most marks are won or lost. For weaknesses, the winning move is always: (1) acknowledge it, (2) explain why it was an acceptable trade-off for a final-year scope, (3) state the exact production fix. Never pretend a known shortcut is secretly fine.

TIER 1 — Opening & project framing (almost certain)

Q1. In one or two sentences, what is this project?
It is an event-driven accounting/ERP platform for Kosovo SMEs, built as six services (gateway, IAM, compliance, operations, ledger, AI) following Domain-Driven Design bounded contexts. It handles incoming bills (fatura hyrëse), sales invoices, inventory, and posts everything to a double-entry general ledger, with Kosovo VAT/SKA compliance rules and an AI assistant for natural-language financial questions.

Q2. What real-world problem does it solve?
Kosovo SMEs need affordable accounting software that already understands local tax law (Law 06/L-032, the SKA standard chart of accounts, NUI business IDs, and EUR). Generic foreign tools don't encode Kosovo VAT categories or the reverse-charge rules, and hiring an accountant is expensive. The system automates double-entry posting and compliance validation so a non-accountant can run the books correctly.

Q3. Why did you choose a microservices architecture rather than a monolith?
The domain splits cleanly into bounded contexts that change at different rates and have different scaling needs — the AI service is memory/CPU heavy and calls an external LLM, while compliance is read-mostly. Independent deployability lets me update tax rules without redeploying the ledger. I also wanted to demonstrate event-driven patterns (outbox, saga, idempotency) that only make sense across service boundaries.

Q4. Be honest — is a microservices architecture actually justified for an SME tool, or is it over-engineering?
For the real-world user count it is arguably over-engineered; a modular monolith would serve the same SMEs with far less operational cost. I'd defend it on two grounds: the bounded contexts are genuine (different data ownership, different change cadence), and the project's academic goal is to demonstrate distributed-systems patterns. In fact the repo keeps a modular-monolith version under src/ precisely to show the same domain can run either way — the split is a deployment decision, not a domain one.

Q5. Why is there both a src/ folder and a services/ folder? Which one is "the system"?
src/ is the original modular monolith — one Nest app wiring IAM, Compliance, and Operations modules together. services/ is the extracted microservices version that docker-compose and Kubernetes actually deploy. They share the same domain model, demonstrating the "start as a modular monolith, extract services along bounded-context seams" strategy. The deployed system is services/; the monolith remains as a reference and as the target of the unit-test suite.

Q6. Your Jest tests only collect coverage from src/, not services/. Isn't that a gap?
Yes, and I'd flag it openly. The domain logic in src/ and services/ is near-identical (aggregates, services were copied during extraction), so the unit tests exercise the same logic, but they don't test the service-specific wiring — the Kafka consumers, the outbox dispatcher, the saga reply handlers. Those are only covered by the e2e/integration specs. In a production setup each service would own its own test suite in its own package.

Q7. What technologies did you use and why?
NestJS + TypeScript for the backend (strong DI, decorators, first-class DDD layering), PostgreSQL per service (one DB per bounded context), Kafka for the event bus, pgvector for AI embeddings, Google Gemini for the LLM, React + Vite + Tailwind for the SPA, nginx as the API gateway, and Docker Compose / Kubernetes for orchestration. TypeORM is the ORM, class-validator for DTO validation.

Q8. What are you most proud of in this codebase?
The event-delivery story: a transactional outbox in operations, idempotent consumers in the ledger, and a choreographed saga with compensation for the storno (reversal) workflow. It means a reversal is eventually consistent and self-healing even if a service crashes mid-flight, without distributed two-phase commit.

Q9. If you had three more months, what would you fix first?
Three things in order: (1) replace the Base64 password placeholder with bcrypt/argon2 and use a vetted JWT library, (2) move money off JavaScript floats onto a decimal type, and (3) persist the audit log and registration codes (currently in-memory) and add saga timeouts so a bill can't get stuck in REVERSING forever.

Q10. Who are the user roles and what can each do?
Four roles in a hierarchy enforced by RolesGuard: admin (40) > accountant (30) > data_clerk (25) > auditor (20). Admin manages users and the business profile, accountant posts and pays documents, data_clerk enters data, auditor has read access. A guard requiring "accountant" admits anyone at level 30 or above.

TIER 2 — Architecture, DDD & bounded contexts (very likely)

Q11. Walk me through the request flow for a typical API call.
Client → nginx gateway (port 3000) which routes /api/v1/<area> to the owning service → the service's Nest controller → application service → domain aggregate. Auth is a Bearer JWT issued by IAM; the gateway forwards it and each service trusts/validates it. The frontend talks only to the gateway, never to services directly.

Q12. What are your bounded contexts and how did you decide the boundaries?
IAM (identity, tenants, auth), Compliance (Kosovo tax taxonomy + rules), Operations (bills, invoices, inventory, EDI, storno orchestration), Ledger (double-entry journal, reports), and AI (insights, NL queries). Boundaries follow data ownership and language: a "bill" is an Operations concept, a "journal entry" is a Ledger concept, and they communicate only through events, never shared tables.

Q13. How do services communicate — synchronously or asynchronously?
Both. Business state changes flow asynchronously via Kafka events (operations → ledger → AI). Cross-tenant lookups and compliance validation are synchronous HTTP calls. I deliberately kept the write-path async (for resilience and decoupling) and the read/lookup-path sync (for simplicity and immediate consistency where it's needed).

Q14. Each service has its own database. Why? What do you lose?
Database-per-service enforces the bounded context at the data layer — no service can reach into another's tables, so they can evolve schemas independently. What I lose is cross-service ACID transactions and easy joins; I compensate with events, the outbox pattern, idempotent consumers, and a saga for the one multi-service workflow (storno).

Q15. Show me how DDD layering appears in the code.
Each service has domain/ (aggregates, value objects, invariants — e.g. FaturaHyrese, BillLine), application/ (services orchestrating use-cases, DTOs), and infrastructure/ (controllers, TypeORM entities, repositories, Kafka adapters). The domain layer has no framework or DB dependency — FaturaHyrese is plain TypeScript with a private constructor and factory methods.

Q16. What is an aggregate, and what is your aggregate root?
An aggregate is a cluster of domain objects treated as one consistency boundary, mutated only through its root. FaturaHyrese (incoming bill) is a root; its BillLine items are value objects inside it. You can't construct an invalid line or an invalid bill — all invariants are checked in the constructors, and state changes go through methods like post(), pay(), reverse().

Q17. Why is FaturaHyrese's constructor private with static factory methods?
To force every creation path through validation and to distinguish "brand new" from "loaded from DB". createNew() generates a UUID and starts in DRAFT; rehydrate() reconstructs an existing bill with its persisted status. A private constructor prevents anyone bypassing those invariants.

Q18. What's the difference between an entity and a value object in your model?
An entity has identity and a lifecycle (the bill, identified by UUID, transitions through states). A value object is defined entirely by its attributes and is immutable (a BillLine — two lines with the same description/quantity/price are interchangeable). My BillLine fields are all readonly and it exposes a computed netAmount getter.

Q19. Where do you enforce business invariants — in the database, the DTO, or the domain?
In three layers, deliberately. DTOs (class-validator) reject malformed HTTP input early. The domain aggregate enforces true business invariants (a bill needs ≥1 line, quantity > 0, valid state transitions). Compliance rules (valid tax category, leaf account codes) are checked via the compliance client. The DB has constraints (unique, not-null) as a last backstop.

Q20. Isn't validating in three places redundant?
There's overlap but each layer has a distinct job: DTO validation protects the HTTP boundary and gives clean 400s; domain invariants protect the model regardless of how it's invoked (including from a Kafka consumer that never sees a DTO); DB constraints protect against bugs in the layers above. Defence in depth is intentional, not accidental duplication.

Q21. How does the gateway know where to route a request?
nginx matches the path prefix: /api/v1/bills, /invoices, /inventory, /operations, /edi → operations:3003; /iam,/auth → iam:3001; /compliance → 3002; /ledger → 3004; /ai → 3005; everything else → the frontend. It uses a dynamic DNS resolver so it re-resolves service IPs as pods restart.

Q22. Why nginx as the gateway rather than an API-gateway product (Kong, Traefik) or Nest itself?
nginx is lightweight, battle-tested for reverse proxying, and zero-cost to run. For this scope I only needed path-based routing and a health endpoint. A product like Kong would add auth plugins, rate limiting, and request transformation — which I'd adopt in production, but they were beyond the project's needs.

Q23. The gateway does no authentication. Where is auth enforced?
Auth is enforced inside each service via the JwtAuthGuard, since each service must independently trust the token (defence in depth). Ideally the gateway would also verify the JWT at the edge to reject unauthenticated traffic early — IAM exposes a /verify endpoint for exactly that — but currently the gateway just proxies.

Q24. What is CQRS and do you use it?
CQRS separates the write model (commands) from the read model (queries). I don't implement full CQRS — services handle both — but there are CQRS-flavoured elements: the ledger maintains an in-memory read projection rehydrated from Postgres, and the AI service builds a separate read model from ledger events. A natural evolution would be event-sourced read projections.

Q25. How would you add a new bounded context, say Payroll?
Create a new service with its own DB, define its aggregates, subscribe it to the events it cares about (e.g. it would publish payrollPosted that the ledger consumes into salary/expense accounts), add gateway routing, and register its compliance rules. The event contracts are the integration surface, so existing services need no changes.

TIER 3 — Event-driven core: Kafka, outbox, saga, idempotency (very likely, high-value)

Q26. Describe the end-to-end event flow when a bill is posted.
Operations commits the bill as POSTED and writes a billPosted row to its outbox table in the same logical operation. A dispatcher publishes it to the operations.events Kafka topic. The ledger consumes it, posts a double-entry journal (expense debit / payable credit), persists it, and publishes journalEntryPosted to ledger.events. The AI service consumes that and updates its per-tenant financial read model.

Q27. What is the transactional outbox pattern and why did you use it?
Instead of writing to the DB and then publishing to Kafka (two systems that can't share a transaction — the "dual write" problem), I persist the event into an ops_event_outbox table as part of the DB write, then a background dispatcher reads PENDING rows and publishes them, marking them PUBLISHED on success. If the broker is down the event isn't lost; it's retried. This guarantees at-least-once delivery without distributed transactions.

Q28. Walk me through your outbox dispatcher implementation.
CrossServiceEventPublisher.flushOutbox() runs on a 1.5-second interval (and immediately after a publish). It selects PENDING or FAILED rows whose nextAttemptAt ≤ now, ordered by creation, in batches of 50. Each is delivered; on success it's marked PUBLISHED, on failure it's marked FAILED with an exponential backoff (2^attempts, capped at 60s) and the error stored. A boolean guard prevents overlapping flushes.

Q29. Your outbox isn't actually written in the same DB transaction as the bill — is it truly transactional?
Correct, and that's a fair challenge. The bill is saved, then the outbox row is saved in a separate call, so there's a narrow window where the bill commits but the outbox insert fails. A fully correct implementation wraps both in one EntityManager transaction. As written it's "outbox-style" and dramatically more reliable than a naive dual-write, but to be rigorous I'd wrap them in a single transaction.

Q30. What delivery guarantee do you have — at-most-once, at-least-once, or exactly-once?
At-least-once. The outbox retries until success, so an event can be delivered more than once (e.g. published, then the PUBLISHED update fails, so it's retried). I make the consumers idempotent so duplicate delivery is harmless — that's how you get effectively-once processing without true exactly-once semantics.

Q31. How exactly do consumers deduplicate?
Every event is enriched with an eventId (UUID) and a deterministic idempotencyKey of the form type:tenantId:entityRef. The ledger keeps a ledger_ingested_events table; before processing it checks whether that idempotencyKey/eventId was already ingested and skips if so, otherwise inserts the marker and proceeds. There's also an in-memory Set fallback when the DB isn't wired.

Q32. There's a race in the dedup check — find-then-insert isn't atomic. Two duplicate events arriving concurrently could both pass. How would you fix it?
Right. The robust fix is to rely on a unique constraint on the idempotency marker and treat an insert conflict as "already processed" — insert first, and if it throws a unique-violation, skip. The code does fall back to catching the save error as a duplicate, but the primary path does a separate findOne first, which has the race. Insert-and-catch (or INSERT ... ON CONFLICT DO NOTHING) closes it.

Q33. Why Kafka specifically, and not RabbitMQ or Google Pub/Sub?
Kafka gives a durable, replayable log — consumers track offsets and can re-read history, which suits an accounting audit trail. Different consumer groups (ledger, AI, the saga consumer) each get the full stream independently. The code is abstracted enough that the docker-compose even ships a Pub/Sub emulator, and the publisher has an HTTP fallback, so the transport is swappable.

Q34. What is the saga pattern and where do you use it?
A saga coordinates a multi-service operation as a sequence of local transactions with compensating actions, instead of a distributed transaction. I use a choreographed saga for storno (reversal): Operations moves the bill to REVERSING and requests a reversal; the Ledger posts the reversing entry and replies; Operations finalizes to REVERTED on success or compensates back to POSTED on failure.

Q35. Walk through the storno saga step by step, including the failure path.
(1) reverseBill() transitions POSTED → REVERSING, persists, publishes billRevertRequested. (2) The ledger finds the original unreversed journal entry, posts a STORNO entry that swaps every line's debit and credit, marks the original reversedBy, and publishes stornoPosted. (3) Operations' saga consumer calls handleStornoPosted() → confirmReversal() → REVERTED. On the failure path the ledger can't find the original, publishes stornoFailed, and Operations calls cancelReversal() → back to POSTED.

Q36. Is this choreographed or orchestrated, and why?
Choreographed — there's no central coordinator; each service reacts to events and emits its own. I chose it because the storno flow is short (two services, two steps) and choreography keeps them decoupled. For a longer workflow with many branches I'd switch to an orchestrator (a saga state machine) because choreography becomes hard to follow as steps multiply.

Q37. What happens if the Ledger never replies — the bill is stuck in REVERSING forever. How do you handle that?
That's a real gap: there's no saga timeout. Today the bill stays REVERSING until a reply arrives. The fix is a timeout/watchdog: persist the saga start time and have a scheduled job that, after N minutes with no reply, either retries the request or moves the bill to a "needs attention" state for manual resolution. A dead-letter queue for poison messages would complement it.

Q38. The saga reply handlers return silently if the bill isn't found or is in the wrong state. Is that safe?
It's idempotent-safe — a duplicate stornoPosted for an already-REVERTED bill is correctly ignored — but it's observability-poor: a reply for a non-existent entity is swallowed with no alert. I'd keep the idempotent guard but log it at warn/error and emit a metric, so genuinely anomalous replies are visible rather than silent.

Q39. Why does the STORNO entry swap debit and credit instead of deleting the original?
Because accounting records are immutable — you never erase a posted entry, you post an equal and opposite reversing entry so the audit trail shows both the original and the correction. Swapping debit↔credit on every line produces a journal that nets the original to zero while preserving history, which is exactly what tax auditors require.

Q40. Both Kafka and HTTP appear as transports. Why the fallback?
Resilience and dev ergonomics. If KAFKA_BROKERS is unset or the broker is unreachable, the publisher posts events directly to the target service's HTTP endpoint (e.g. /api/v1/ledger/events), and the saga reply has an HTTP fallback to /operations/saga/storno-reply. It means the system runs locally without Kafka and degrades gracefully if Kafka is down.

Q41. With a single Kafka partition, can you guarantee event ordering?
Within one partition, yes — Kafka preserves order per partition, and I key messages by tenantId so a tenant's events land on the same partition and stay ordered. With one partition globally everything is ordered but throughput is capped at one consumer. Scaling to multiple partitions keeps per-tenant ordering (because of the key) while allowing parallelism.

Q42. If you scale the ledger to multiple consumer instances, what breaks?
The in-memory mem projection: each instance would hold only the entries from its assigned partitions, so a trial-balance query hitting one instance would be incomplete. The fix is to compute reports from Postgres (the source of truth) rather than the in-memory array, or to make the read API query the DB directly. The dedup table is already shared via Postgres so idempotency survives scaling.

Q43. What is a consumer group and how do you use them?
A consumer group is a set of consumers that share a topic's partitions so each message is processed once per group. The ledger's operations-consumer, the AI's ledger-consumer, and Operations' storno-saga consumer each use distinct group IDs, so they independently receive the streams they care about — AI and the saga consumer both read ledger.events but in separate groups, so both see every message.

Q44. Your Kafka consumers catch parse errors and just log them — won't that drop events?
Yes — a malformed message is logged and skipped, with no retry or dead-letter. For transient handler failures that's a real risk of silent loss. Production-grade handling would commit offsets only after successful processing, retry with backoff, and route poison messages to a dead-letter topic for inspection rather than dropping them.

Q45. How do you prevent an infinite event loop (ledger → AI → ledger …)?
The topology is acyclic by design: Operations publishes to operations.events, the ledger consumes that and publishes to ledger.events, and AI only consumes ledger.events and never publishes back. No consumer emits to a topic that eventually feeds itself, so there's no cycle.

Q46. The idempotencyKey is type:tenantId:entityRef. What if two legitimately different events produce the same key?
That's the risk to watch. For example two payments against the same reference could collide if entityRef isn't unique per event instance. For payments the reference is suffixed (-PAYMENT), but the general lesson is the key must include something that distinguishes distinct business events. Where it can't, I rely on the unique eventId as the real dedup anchor.

Q47. How would you replay events to rebuild the AI read model from scratch?
Because Kafka retains the log, I'd reset the AI consumer group's offset to the beginning of ledger.events and let it re-consume. The ingestion is additive per tenant, so I'd first clear the AI state/vector store, then replay. This is a key reason I chose Kafka over a fire-and-forget bus.

TIER 4 — Accounting domain: double-entry, ledger, VAT, reports (very likely)

Q48. Explain double-entry bookkeeping and how your ledger implements it.
Every transaction affects at least two accounts so that total debits equal total credits. My ledger posts each event as a two-line journal entry — e.g. a posted bill debits an operating-expense account and credits accounts payable for the same amount. The getSummary() method reports whether total debits and credits are balanced within a cent.

Q49. Critical: do you actually enforce that debits equal credits when posting?
No — and this is the sharpest accounting critique. The ledger constructs balanced pairs in code, so in practice they balance, but there's no guard rejecting an entry where sum(debits) ≠ sum(credits). A corrupt upstream event could post an unbalanced entry. The fix is a single invariant check in the posting path that throws if the lines don't balance — cheap and essential for a financial system.

Q50. Even bigger: I don't see VAT posted anywhere. Where does VAT go in your journal entries?
You've found the most important accounting gap. The events carry totalNetAmount and the ledger posts net expense/payable (or receivable/revenue) — it never posts the VAT to a separate VAT-receivable/payable account, even though the bill lines carry a taxCategoryId and the chart of accounts has a VAT account (250). So the books are net-only. To be tax-correct, posting a bill should be a three-line entry: expense (net) debit, VAT input debit, payable (gross) credit. I'd present this as the top correctness fix.

Q51. So your trial balance and reports exclude VAT entirely?
Yes — because VAT is never posted, the trial balance, P&L and balance sheet are all on a net basis. For an SME's internal P&L that's still informative, but it's not a fil-ready VAT position. Fixing the posting (Q50) automatically flows VAT into the trial balance and enables a proper VAT return.

Q52. How are monetary amounts represented? Any precision concerns?
They're JavaScript number (IEEE-754 doubles). I round to two decimals with Math.round(x*100)/100 in reports. The concern is real: floating-point can't represent values like 0.1 exactly, and errors can accumulate over many lines. For a financial system the correct choice is a decimal type (decimal.js / big.js) or integer minor units (cents), with rounding only at well-defined points.

Q53. At what scale does the float issue actually bite?
For a handful of lines it's invisible — the two-decimal rounding masks it. It becomes material when you sum thousands of fractional values or chain multiplications (quantity × unit price × tax) without rounding between steps. The honest answer is: it hasn't caused a visible bug at demo scale, but it's a latent correctness risk that a real deployment must remove.

Q54. Walk me through the journal entries for the full bill lifecycle.
On billPosted: debit operating expense (665-09), credit accounts payable (220). On billPaid: debit accounts payable (220), credit cash (100) — settling the liability. On storno: a STORNO entry reversing the original lines. Each is balanced and tagged ORIGINAL or STORNO with the bill reference.

Q55. And for a sales invoice?
On invoiceCreated: debit accounts receivable (140), credit revenue (700). On invoicePaid: debit cash (100), credit accounts receivable (140). invoiceSent is a commercial state change with no accounting posting — recognition happens at creation.

Q56. How do inventory movements hit the ledger?
A RECEIPT debits inventory (125) and credits payable (220). An ISSUE debits cost of goods sold (500) and credits inventory (125). So the ledger tracks stock value and COGS automatically from the inventory events.

Q57. What is the SKA chart of accounts and how is it encoded?
SKA is Kosovo's standardized chart of accounts. In the ledger it appears as a constant map of codes (100 cash, 125 inventory, 140 receivable, 220 payable, 500 COGS, 700 revenue, 665-09 other operating expense), and the compliance service holds the fuller hierarchical taxonomy (~45 accounts with parent/child and types).

Q58. What is the LEGACY_TO_SKA_ACCOUNT map for?
It normalizes older 4-digit codes (1000, 2000, 4000…) to current SKA codes (100, 220, 700…). Historical entries or alternate inputs get mapped to the canonical code before aggregation, so the trial balance and reports group consistently regardless of which code style produced the entry.

Q59. How is the trial balance computed?
getTrialBalance() iterates the tenant's in-memory entries, sums debits and credits per (normalized) account, and returns each account's totals plus its net balance, rounded to cents. It's an aggregation over the journal — the classic trial balance.

Q60. How do you generate the P&L and what assumptions does it bake in?
generateProfitLossCsv() filters entries to a quarter and classifies by account-code prefix: 7xx as revenue, 500 as COGS, 6xx as operating expenses; gross profit = revenue − COGS, net = gross − opex. The CSV is in Albanian with TAK headers. The baked-in assumption is that the prefix convention holds — if SKA reclassifies a code, the report logic must change with it.

Q61. Your balance sheet uses prefix sums and Math.max(0, …). Walk me through it and its risks.
generateBalanceSheetCsv() nets each account (debit − credit) as of quarter-end, then sums prefix '1' as assets, '2' as liabilities (sign-flipped), and sets equity = assets − liabilities. The Math.max(0, …) clamps negatives to zero, which hides legitimately negative balances (e.g. an overdrawn cash account) and forces the sheet to "look" balanced rather than proving it. A correct balance sheet should derive equity from actual equity/retained-earnings accounts and never clamp.

Q62. Does your balance sheet actually prove assets = liabilities + equity, or assume it?
It assumes it — equity is defined as assets − liabilities, so the identity holds by construction rather than by independent measurement. A real balance sheet computes equity from equity-class accounts (300/310/320) and uses the accounting equation as a check; if it doesn't balance, that signals an error. Mine can't detect such an error.

Q63. There's a ledger-closed-period entity in the codebase — is period locking implemented?
The entity exists, so the data model anticipates closed periods, but the posting path doesn't yet consult it — entries can be back-dated into any period. So it's modelled but not enforced. Enforcement would mean checking, before posting, that the entry's date isn't in a closed period and rejecting it if so.

Q64. Why is the ledger held in memory and rehydrated from Postgres?
For fast read aggregations (trial balance, reports) without round-tripping the DB on every query. On startup onModuleInit() loads all entries into the mem array; writes go to both memory and Postgres. The trade-off is memory growth and the multi-instance problem (Q42) — at scale the reads should move to SQL aggregation.

Q65. Is the ledger append-only? Can an entry ever be mutated?
Effectively append-only for accounting purposes: corrections are new STORNO entries, never edits. The one mutation is setting reversedBy on the original to link it to its reversal. There's no API to delete or alter the amounts/lines of a posted entry, which preserves the audit trail.

Q66. How would you support multi-currency? Right now everything is EUR.
Currency is stored on the bill but reports hardcode EUR. I'd add an exchange-rate service, store both transaction currency and a base-currency amount on each entry (with the rate and date used), and post in base currency while retaining the original. Reports would then aggregate in base currency. It's a sizeable change because every amount becomes a (value, currency, rate) triple.

Q67. What does the inventory weighted-average cost calculation do?
On a RECEIPT it recomputes the average unit cost: (oldQty×oldAvg + qty×newCost) / (oldQty+qty), and increases quantity on hand. On an ISSUE it values the issue at the current average and decrements quantity, refusing to issue more than is on hand. Valuation is Σ(quantity × average cost) per SKU.

Q68. Why weighted-average rather than FIFO or LIFO?
Weighted-average is simplest to implement correctly and is acceptable under most accounting standards for SMEs; it avoids tracking individual cost layers. FIFO would require a queue of cost lots per SKU and is more faithful in inflationary conditions; LIFO is disallowed under IFRS. For the target users, weighted-average is a defensible, standard choice.

Q69. If you reverse a bill that contained inventory items, does the inventory reverse too?
No — and that's a consistency gap. Bill reversal and inventory reversal are decoupled; the storno saga reverses the journal but doesn't emit compensating inventory movements. A correct design would have the bill reversal also trigger reversing inventory movements (or model them as part of the same saga), otherwise stock and books drift apart.

Q70. Could inventory go negative under concurrency?
Yes. The check "on-hand ≥ requested" and the decrement aren't atomic, and state lives in an in-memory map, so two concurrent ISSUEs could both pass the check and drive quantity negative. The fix is a per-SKU lock or an atomic conditional DB update (UPDATE … SET qty = qty - :n WHERE qty >= :n) that fails if it would go negative.

TIER 5 — Security & authentication (very likely — expect probing)

Q71. How are passwords stored?
Honestly: as Base64 of the plaintext, with a code comment flagging it as a demo placeholder. Base64 is encoding, not hashing — it's fully reversible, so it provides no protection if the database leaks. This is the single most important thing to fix and I'd say so up front.

Q72. Why is Base64 not acceptable, and what should you use?
Hashing must be one-way and slow, with a per-user salt, so an attacker who steals the DB can't recover passwords or run fast offline guessing. Base64 is instantly reversible. The correct choice is a memory-hard adaptive hash — argon2id (preferred) or bcrypt — with a salt and a tuned work factor. It's a few-line change: hash on registration, compare with the library's verify on login.

Q73. How are your JWTs created and verified?
Hand-rolled HS256: the service base64url-encodes a header and payload, signs with HMAC-SHA256 over a secret, and on verification re-splits the token, recomputes the signature, and checks expiry, tenantId and role. It's functionally a JWT but implemented manually rather than via a vetted library.

Q74. What's wrong with implementing JWT yourself?
Crypto you write yourself is easy to get subtly wrong — constant-time signature comparison, algorithm confusion (the "alg: none" attack), correct base64url handling, claim validation. A maintained library (jsonwebtoken, jose, or Nest's @nestjs/jwt) has handled these and is audited. I'd swap to one; the manual version was to understand the mechanics, not for production.

Q75. Your JWT secret falls back to a hardcoded default. Why is that dangerous?
If JWT_SECRET isn't set it defaults to a string committed in the source. Anyone who reads the repo can forge a token for any tenant and role — full authentication bypass. Production must fail to boot if the secret is absent, and the secret must come from a secret manager, never source. The k8s secret also ships with a placeholder value that must be replaced.

Q76. What's in your JWT payload and why include tenantId?
sub (user id), email, tenantId, role, mustChangePassword, iat, exp. tenantId is included so every downstream service can scope data to the caller's tenant without an extra lookup — it's the backbone of multi-tenant isolation. The trade-off is that tenant/role are baked in until the 8-hour token expires.

Q77. There's no refresh token and an 8-hour expiry. What are the implications?
Users are silently logged out at 8 hours, and there's no way to revoke a token early — if a token leaks it's valid until expiry. A refresh-token scheme would let me issue short-lived access tokens (minutes) plus a revocable refresh token, shrinking the exposure window and enabling logout/revocation. As-is, the only mitigation is the relatively long-but-bounded lifetime.

Q78. How do you revoke a compromised token today?
You can't, cleanly — JWTs are stateless and there's no deny-list. Options I'd add: a short access-token TTL with refresh tokens, a server-side token blacklist keyed by jti, or rotating the signing secret (which nukes all sessions). For now the honest answer is revocation isn't supported.

Q79. How do services authenticate to each other (e.g. Operations → IAM internal lookup)?
Via a shared secret header x-operations-secret checked against IAM_OPS_SHARED_SECRET. It gates the internal NUI-lookup endpoints. The weakness is a hardcoded dev fallback value and a single static secret; a stronger design uses mutual TLS or signed service tokens (e.g. SPIFFE/mTLS in the mesh) with rotation.

Q80. The x-tenant-id header drives data scoping but isn't checked against the JWT. Can a user read another tenant's data?
This is the biggest authorization risk. Several services trust x-tenant-id from the header and even default it to 'public' if missing, rather than deriving the tenant from the verified JWT. A caller who sets another tenant's id could read their data. The correct design is to ignore the header and take tenantId from the authenticated token claim, or to verify the header matches the claim.

Q81. So is tenant isolation actually enforced?
Data is filtered by tenantId everywhere — repositories, queries, the vector store — so isolation is implemented at the application layer. But because some entry points trust a client-supplied tenant id, the enforcement is only as strong as that trust. Tightening it to the JWT claim, plus Postgres row-level security as defence in depth, would make it robust.

Q82. Is there rate limiting or brute-force protection on login?
No — there's no throttling on login or registration, so credential stuffing and brute force aren't mitigated. I'd add a rate limiter (Nest's ThrottlerGuard or at the gateway), account lockout/backoff after repeated failures, and ideally CAPTCHA on registration. The registration code flow does cap verification attempts at 5, which is a partial control.

Q83. Where is the audit log stored?
In an in-memory ring buffer capped at 500 entries in IAM (and ~100 in Operations' activity log). That means it's lost on restart and can't serve a real audit. For a financial/regulated system the audit trail must be persisted to the database (append-only, ideally tamper-evident). It's currently a functional demo, not a compliance-grade log.

Q84. Registration/verification codes are also in memory — what's the consequence?
A 4-digit code with a 10-minute TTL is held in a Map; if the service restarts, pending registrations are lost, and across multiple replicas the code isn't shared so verification can hit the wrong instance. It should live in a shared store (Postgres or Redis) with a TTL. Also, 4 digits is low entropy — I'd lengthen it and rate-limit attempts (attempts are capped at 5, which helps).

Q85. Is traffic encrypted? I don't see TLS in the ingress.
Locally it's plain HTTP, and the k8s ingress has no TLS section, so JWTs would travel in clear text — vulnerable to interception. Production must terminate TLS at the ingress (cert-manager + Let's Encrypt) and ideally use mTLS between services. This is a deployment hardening item rather than an app-code change.

Q86. How does the frontend store the JWT, and what's the risk?
In localStorage under guri_token. The risk is XSS: any injected script can read localStorage and exfiltrate the token. The more secure pattern is an httpOnly, Secure, SameSite cookie set by the backend so JavaScript can't read it, combined with CSRF protection. localStorage was chosen for simplicity with a token-in-header API.

Q87. Are you vulnerable to SQL injection?
Largely no for the ORM paths — TypeORM uses parameterized queries, and the pgvector raw SQL in the AI service uses bound parameters. The thing to watch is any place that builds SQL by string concatenation; I avoided that. The bigger input-validation story is class-validator on DTOs rejecting malformed payloads.

Q88. Is CORS configured safely?
The monolith enables CORS from ALLOWED_ORIGINS or * as a fallback with credentials. Wildcard origin plus credentials is not allowed by browsers and is unsafe in general; production must pin explicit origins. It's a permissive dev default that needs locking down.

Q89. What does mustChangePassword do and why?
When an admin creates a user, the account is flagged to force a password change on first login, so the admin-set temporary password can't persist. The flag rides in the JWT and the login response so the UI can route the user into the change-password flow. It's a small but real security control.

Q90. How is the NUI (business ID) validated, and is it enough?
With the regex ^8\d{8} — nine digits starting with 8 — at both the DTO and entity level, plus a uniqueness check in the service. It validates format and uniqueness but not that the NUI is a real registered business; a production system would verify against Kosovo's business registry.

TIER 6 — Multi-tenancy & data isolation (likely)

Q91. What multi-tenancy model did you choose — silo, bridge, or pool?
Pool (shared database, shared schema) with a tenantId discriminator column on every row. It's the cheapest and simplest to operate for many small tenants. The trade-off is that isolation depends on always filtering by tenantId in code; a missed filter leaks data, which is why row-level security would be a valuable backstop.

Q92. How is a tenant created?
Registration creates a Tenant (name, slug, NUI) and its first admin User together. The tenant id then appears in every JWT issued to that tenant's users and scopes all their data across services.

Q93. How would you move a noisy or large tenant to its own database?
Because every row carries tenantId and services own their data, I could migrate that tenant's rows to a dedicated DB and route its requests there (a "bridge"/"silo" per-tenant routing). The app already keys everything by tenant, so the main work is connection routing and the data move, not a domain rewrite.

Q94. Could you add Postgres row-level security?
Yes, and I'd recommend it. I'd set a session variable (e.g. app.tenant_id) from the verified JWT on each request and define RLS policies that restrict every table to matching rows. Then even a forgotten WHERE tenantId = … can't leak data — the database enforces it. That's the proper defence-in-depth answer to Q80/Q81.

Q95. How does cross-tenant invoicing (EDI) respect isolation?
When company A sends an invoice to company B, A only supplies B's NUI; IAM resolves it to B's tenant id via an authenticated internal lookup, and an EDI inbox item is created under B's tenant. Neither side reads the other's tables — the document is copied across the boundary as a snapshot, preserving isolation.

Q96. What stops tenant A from enumerating tenant B's bills by guessing UUIDs?
Currently only the application's tenantId filter, and — as noted — some endpoints trust the header. UUIDv4 ids are unguessable in practice, but security shouldn't rest on that. Deriving tenant from the JWT plus RLS is the real protection.

Q97. The default tenant is 'public' when no header is present. Why, and is it a risk?
It was a convenience so endpoints work in local testing without auth wiring. It's a risk because unauthenticated or header-less calls land on a shared 'public' tenant. In production I'd remove the default and reject requests without an authenticated tenant.

Q98. Do all five services agree on what a tenant is?
Yes — tenantId (a UUID) is the shared identifier across all services and events. IAM is the source of truth that mints it; everyone else treats it as an opaque scoping key carried in the JWT and on every event.

TIER 7 — AI service, RAG & Gemini (likely — it's a headline feature)

Q99. What does the AI service actually do?
It maintains a per-tenant financial read model from ledger events (total expenses, entry count, history), generates rule-based insights (e.g. expense-spike warnings), and answers natural-language questions about a tenant's finances using Retrieval-Augmented Generation over Gemini, grounded in the tenant's data plus the Kosovo compliance corpus.

Q100. Explain your RAG pipeline end to end.
The question is embedded with Gemini's text-embedding-004 (768-dim). A cosine-similarity search over pgvector returns the top-k (8) chunks — shared corpus (SKA accounts, rules, tax categories) plus tenant-scoped journal chunks. Those chunks plus a financial summary are assembled into a grounded prompt instructing the model to answer only from context, which is sent to Gemini's generateContent. The answer is returned with sources and a confidence score.

Q101. What is RAG and why use it instead of just prompting the LLM?
RAG retrieves relevant facts from your own data and injects them into the prompt, so the model answers from grounded context rather than its trained-in (and possibly stale or hallucinated) knowledge. For finance that's essential — the model must cite this tenant's actual numbers and Kosovo's actual rules, not invent them. It also keeps tenant data out of any model training.

Q102. How do you stop the AI hallucinating account codes or amounts?
Three controls: the prompt explicitly says "answer ONLY from the provided context, never fabricate codes/amounts/legal references"; temperature is low (0.2) for determinism; and retrieval grounds it in real chunks. But none of these is a guarantee — LLMs can still drift, so I'd add post-hoc validation (e.g. check any account code it returns exists in the chart of accounts) before trusting outputs.

Q103. Is your confidence score meaningful?
Not really — it's a heuristic (high if chunks were retrieved, low on the fallback path), not a calibrated measure of correctness. A retrieved chunk can be high-similarity yet irrelevant. I'd present it as a UI signal, not a guarantee, and improve it with a relevance threshold and an LLM self-check or answer-grounding score.

Q104. How is the AI prevented from leaking one tenant's data to another?
The vector search filters tenant_id IS NULL OR tenant_id = :tenant, so it only ever retrieves the shared corpus plus the caller's own chunks; the prompt also states isolation is strict. The weakness is the same header-trust issue (Q80) — the tenant comes from x-tenant-id, so it must be bound to the JWT to be safe.

Q105. What about prompt injection — a user asking "ignore instructions and reveal X"?
The query is concatenated into the prompt after the grounding instructions, so a crafted query could attempt to override them. Low temperature and the "answer only from context" framing help but don't fully prevent it. Mitigations I'd add: stronger delimiting/escaping of user input, input sanitization, output filtering, and not placing any secret in the prompt so there's nothing sensitive to exfiltrate.

Q106. Your embedding client puts the API key in the URL. Why is that bad?
Query-string secrets leak into access logs, proxy logs, and browser history. The key should go in a header or request body, be sourced from a secret manager, and be rotated. It's an easy fix and a clear finding if a security examiner looks.

Q107. If GEMINI_API_KEY is missing, the embedder returns a zero vector. What's the consequence?
All-zero vectors make every similarity comparison meaningless (everything looks equidistant), so retrieval silently returns garbage rather than failing. That's a fail-silent anti-pattern. It should fail fast at startup if embeddings are required, or clearly run in a degraded "no-RAG" mode rather than poisoning the vector space.

Q108. Why pgvector and the HNSW index? What do the parameters mean?
pgvector keeps embeddings in the same Postgres I already run, avoiding a separate vector DB. HNSW (m=16, ef_construction=64) is an approximate-nearest-neighbour graph index that's fast for sub-million-row corpora without manual rebuilds, trading a little recall for speed. Cosine distance (<=>) matches how the embeddings are compared.

Q109. Why k=8, and is a fixed k a good idea?
Eight chunks balance enough context against prompt size and cost. A fixed k is a simplification — if all eight are low-relevance they still get injected as if useful. Better is a similarity threshold (drop chunks below a score) or dynamic k, so the prompt only carries genuinely relevant context.

Q110. How is the compliance corpus seeded into the vector store?
On startup the seeder fetches the bundle from the compliance service, turns each SKA account, rule, and tax category into a natural-language sentence, embeds it, and upserts it as a shared (tenant_id NULL) chunk. Upserts are idempotent via a deterministic logical key, so re-seeding doesn't duplicate.

Q111. The seeder skips if the existing count ≥ bundle count. What bug does that hide?
If the taxonomy changes without growing — e.g. an account is renamed or one is removed and another added — the counts can match while content is stale, so the corpus never updates. A content hash or version check would be correct rather than a count comparison.

Q112. Why is indexing fire-and-forget? What if it fails?
To keep event ingestion fast and non-blocking — the financial state updates immediately and embedding happens in the background. The downside is that if the embedding call fails, that entry is never searchable and nothing retries it. A durable job queue with retries (or marking un-indexed rows and a sweeper) would fix it.

Q113. Why temperature 0.2 rather than 0 or something higher?
Low temperature makes answers more deterministic and less inventive, which is what you want for financial Q&A. I didn't use exactly 0 to retain a little natural phrasing, but 0 would be a defensible choice for maximum determinism. High temperature would increase hallucination risk, so it's avoided.

Q114. What happens to AI answers if Gemini is unreachable?
The service falls back to returning the financial snapshot/summary without LLM phrasing and a reduced confidence, so it degrades rather than erroring. That keeps the feature usable offline but obviously without natural-language synthesis.

Q115. Does the AI service read other services' databases directly?
No — it owns guri_ai and builds its model purely from ledger.events plus the compliance bundle over HTTP. The docker-compose passes other DB envs to it, but the runtime design is event-driven, preserving the bounded-context rule that a service doesn't reach into another's data. One gap: it can't back-fill history on first start except by replaying the Kafka log.

Q116. Are you sending tenant financial data to a third party (Google)? Privacy implications?
Yes — RAG chunks and the question go to Gemini, which is an external processor. For GDPR that needs a data-processing agreement, data-minimization (send only what's needed, avoid personal data — which the compliance rules already discourage in descriptions), and ideally a region-appropriate or self-hosted model option. It's an important compliance consideration I'd flag.

TIER 8 — Compliance & Kosovo tax domain (likely)

Q117. What does the compliance service own?
The Kosovo tax taxonomy: VAT categories (rates and legal basis), the SKA chart of accounts, and a set of compliance rules (bill/invoice/journal/GDPR/accounting contexts). It distributes them as a versioned bundle and offers a validation endpoint that checks bills/invoices/inventory payloads against the rules.

Q118. Why is the taxonomy hardcoded in code rather than in a database or admin UI?
For this scope the rules are stable and small, so an in-memory, version-controlled taxonomy is simple, fast, and auditable via git. The cost is that changing a rate requires a code deploy. Production would externalize it to a database or rules store with an admin UI and effective-dated rates so non-developers can update tax law.

Q119. Kosovo VAT changes to a new rate next year — what do you do today, and what should you do?
Today: edit the taxonomy constant and redeploy compliance, then services refresh the bundle. The problem is there's no rate history — historical documents would need the old rate. The right model is effective-dated rates (each rate valid from/to a date) so a 2025 bill uses the 2025 rate and a 2026 bill the new one.

Q120. How do other services get the rules, and how do they learn about changes?
They pull the bundle over HTTP — the operations service caches it on startup and polls periodically (and falls back to a hardcoded set if compliance is down). There's no push/invalidation, so updates propagate on the next poll. An event-based "rules changed" signal would make propagation immediate.

Q121. What's in the validation engine?
Context-specific checks: currency must be EUR, dates sane (no far-future issue date, due ≥ issue), at least one line, valid tax category per line, quantity > 0, unit price ≥ 0, account codes valid/leaf/correct type, and GDPR checks that descriptions/IDs don't contain personal data (email/phone/personal-number/card-like patterns).

Q122. The personal-data detection is regex-based. What are its false positives/negatives?
It flags emails, long digit runs (card-like), 10-digit personal numbers, and phone-like strings — but a long invoice or reference number can false-positive, and it misses names or addresses entirely (false negatives). It's a lightweight GDPR guardrail, not real PII detection; a production system would use a proper PII classifier and explicit fields rather than scanning free text.

Q123. What is "leaf account" validation and why does it matter?
Postings must go to leaf accounts (e.g. 665-09), not parent/summary accounts (665), so totals roll up correctly. The chart of accounts is hierarchical with parent codes, and rule CR-009 enforces leaf-only posting. It mirrors how real accounting software prevents posting to header accounts.

Q124. What is reverse-charge VAT and do you model it?
Reverse charge shifts VAT accounting from the supplier to the buyer (common on imports/EU services) — the buyer records both the output and input VAT. The taxonomy includes reverse-charge categories (e.g. category 28 and an RC-credit category), so the classification exists. But since VAT isn't posted to the ledger at all (Q50), the reverse-charge accounting entries aren't actually produced yet.

Q125. The compliance endpoints are unauthenticated. Is that a problem?
They're read-only reference data (tax rates, account codes) meant for internal consumption behind the gateway, so the exposure is low. Still, in production I'd at least restrict them to the internal network/service identity and rate-limit the public-facing ones to prevent abuse of the validate endpoint.

Q126. How is localization handled in compliance?
Endpoints accept an x-lang header; rules are translated EN/SQ, and tax/account names are provided with English translations layered over Albanian source. It's pragmatic but uneven — rules are fully bilingual while some names aren't — which I'd unify with a proper translation table.

Q127. Operations falls back to hardcoded rules if compliance is unreachable. Fail-open or fail-closed?
It fails open — it validates against a cached/hardcoded rule set and lets the operation proceed. For availability that's pragmatic, but for a compliance control fail-open is risky: during a compliance outage invalid documents could slip through. A stricter mode would fail closed for the rules that are legally material and only fall back for non-critical ones.

TIER 9 — Persistence, repositories & data (likely)

Q128. Why TypeORM, and what are its downsides here?
TypeORM integrates cleanly with Nest's DI and decorators and let me map aggregates to tables quickly. Downsides: it doesn't support pgvector columns (hence raw SQL in the AI service), its synchronize/migration story needs care in production, and active-record/data-mapper mixing can get confusing. For vectors I dropped to a raw pg.Pool.

Q129. Your repositories keep an in-memory Map plus an optional ORM. Why, and what's the risk?
The dual mode lets the app run without a database (in-memory) for tests/local dev, and persist when a DB is wired. The risk is cache coherence — the in-memory copy can diverge from the DB if another instance writes, and there's no invalidation — plus unbounded memory growth. In production I'd drop the in-memory store and rely on the DB with proper caching where needed.

Q130. How do you map a domain aggregate to a database row and back?
The repository converts the aggregate to an ORM entity on save (e.g. bill → BillOrmEntity with lines stored as JSONB, dates as ISO strings) and reconstructs it via FaturaHyrese.rehydrate() on read. The domain object never knows about TypeORM — the mapping is the repository's job, keeping the domain layer pure.

Q131. You store line items as JSONB rather than a child table. Why, and what do you lose?
JSONB keeps the aggregate together — one row, one read, matching the DDD idea that lines live inside the bill aggregate. What I lose is easy relational querying (e.g. "all lines posting to account X" needs JSON operators or a scan) and column-level constraints on lines. For an aggregate that's always loaded whole, JSONB is a reasonable fit.

Q132. How are schema changes / migrations handled?
This is a weak spot — the project leans on TypeORM entity definitions and manual/synchronize-style setup rather than a disciplined, versioned migration pipeline. Production needs explicit migration files run as a deploy step, never auto-synchronize against a production DB. The AI service even has a manual ALTER TABLE note for the vector column, which underscores the need.

Q133. The dedup and outbox tables grow forever. What's your retention plan?
There isn't one yet, and at scale those tables would slow lookups. I'd add retention: archive/delete PUBLISHED outbox rows after a window, and age out old idempotency markers once events are far enough in the past that re-delivery is impossible. Both can be periodic jobs.

Q134. Why one Postgres per service rather than schemas in one instance?
Physical separation makes the bounded context's data ownership unambiguous and lets each DB be sized, backed up, scaled, and secured independently (the AI DB even uses the pgvector image). Schemas in one instance would be cheaper to operate but couple availability and blast radius. For the demo it's separate instances; a cost-conscious deployment might consolidate to schemas.

Q135. How do you guarantee consistency between Operations and Ledger without a shared transaction?
Eventual consistency via the outbox + idempotent consumer + saga. Operations commits locally and reliably emits the event; the ledger reliably and idempotently applies it; the storno saga reconciles multi-step flows with compensation. There's a brief window where Operations shows POSTED before the ledger has the entry, which is acceptable for this domain.

TIER 10 — Testing, quality & CI (likely)

Q136. What's your overall testing strategy?
A test pyramid: many unit tests for domain logic and services (Jest), integration/e2e tests over HTTP (supertest), property-based tests for invariants (fast-check), a frontend unit test and a Playwright smoke test, plus a k6 load test and a custom coverage gate enforcing 70% across statement/branch/condition metrics.

Q137. Explain your custom coverage gate — what are the four metrics?
coverage-metrics.mjs reads Istanbul's output and reports: statement coverage; decision (branch) coverage; condition coverage (share of binary/conditional sub-expressions executed); and a decision/condition composite (harmonic mean of the two). It's a JS-tooling analogue of MC/DC-style rigor, since JS lacks a true MC/DC engine. The build fails under 70% on any metric.

Q138. Why did you build a custom gate instead of using Jest's coverage thresholds?
Jest thresholds only cover statements/branches/functions/lines. I wanted condition-level and decision/condition coverage to argue about logical-operand testing, which Istanbul exposes in its raw branch map but Jest doesn't threshold. The script computes those from coverage-final.json. It's a way to demonstrate deeper coverage analysis.

Q139. What is property-based testing and what do you test with it?
Instead of fixed examples, fast-check generates many random inputs and checks that a property holds. I test that a bill line's netAmount always equals quantity × unit price across generated values. It's good at finding edge cases example tests miss.

Q140. Your property suite tests only one property over 50 runs. Isn't that thin?
Fair — it's a demonstration of the technique more than thorough coverage. I'd extend it to tax computation, weighted-average cost invariants (e.g. average cost stays within min/max of inputs), and date-range logic, and raise the run count to hundreds. One property is a starting point, not the finish line.

Q141. Frontend test coverage is very thin — one unit test and one smoke test. Why?
I prioritized backend correctness (where the money logic lives) and treated the UI as a thin client. That's a defensible prioritization for limited time but a genuine gap: there are no page/component tests and no full e2e user journey. I'd add React Testing Library tests for the pages and a Playwright flow (register → login → create bill → see it in the ledger).

Q142. How do you test event-driven code and sagas?
The domain/service logic (state transitions, storno confirm/cancel) is unit-tested directly, and there's a storno-workflow e2e spec. What's not tested is true Kafka ordering/delivery under failure — those are hard in unit tests and would need test containers (a real Kafka in CI) to exercise the consumer/idempotency paths properly.

Q143. What's not covered by your tests that worries you most?
Concurrency (double-posting, inventory oversell races), the actual VAT/accounting correctness end-to-end, multi-instance ledger behaviour, and security authorization paths (e.g. a data_clerk being refused the audit endpoint at the HTTP layer). Those are exactly the areas where a finance system fails dangerously, so they'd be my next tests.

Q144. How does the k6 load test work and what does it measure?
It ramps virtual users (5 → 10 → 20 over 60s) and exercises create-bill, post-bill, trial-balance, and journal-entries endpoints, recording per-operation latency (p95/p99) and success rates. It characterizes throughput/latency under sustained load, though it doesn't profile memory or DB query plans.

Q145. Why exclude DTOs, the event bus, and the repositories from coverage collection?
DTOs are declarative (decorators only), so coverage is noise; the event bus and repositories were excluded mainly because they're infrastructure with heavy I/O that's awkward to unit-test meaningfully. It's a pragmatic choice, but excluding the event bus is debatable since it's important — I'd prefer to test it with fakes rather than exclude it.

TIER 11 — Frontend (moderately likely)

Q146. Describe the frontend architecture.
A React 18 + TypeScript SPA built with Vite, routed by React Router, styled with Tailwind, talking to the gateway via an Axios client with an interceptor that injects the Bearer token, x-tenant-id, and x-lang. Five feature pages (IAM, Daily Ops, Compliance, Ledger, AI) plus a Layout and an ErrorBoundary. State is local React useState; auth/user live in localStorage.

Q147. Why no Redux/Zustand/Context for state?
Each page is largely self-contained CRUD with little cross-page shared state, so local state plus localStorage for the session was enough and avoided boilerplate. The cost shows in the larger pages (Daily Ops holds many useState variables); if shared state or caching grew I'd introduce React Query for server state and possibly Zustand for the little global state there is.

Q148. How does role-based routing work on the client?
A Protected wrapper checks the stored user's role against an allowed-roles list before rendering a route, and the Layout shows navigation by role. This is UX gating only — the real enforcement is the backend guards, since client checks can be bypassed.

Q149. How is internationalization implemented?
A tiny custom i18n: a tr(en, sq) helper picks the string by current language, persisted in localStorage, with a CustomEvent + useLanguage hook to re-render on change. It's dependency-free but the translations are inline dual-strings scattered across pages, which doesn't scale to more languages — a key-based library (react-i18next) with translation files would.

Q150. Several API calls swallow errors. What's the user impact?
Silent .catch blocks can leave stale data or give no feedback on failure, which is poor UX and can mask backend problems. I'd add consistent error handling — toasts/inline messages, a global Axios response interceptor for 401→logout and 5xx→notify, and loading/error states per page.

Q151. The Axios interceptor is set up in two places. Why, and is that a bug risk?
It's redundancy from the build-out — both main.tsx and api/client.ts configure headers. It's a maintenance hazard (change one, forget the other). I'd consolidate to a single shared client module imported everywhere.

Q152. How does the AI chat page work?
It posts the user's question to /api/v1/ai/query, then renders the answer with a confidence percentage and the cited sources, offers suggested-question chips, shows a loading state, and auto-scrolls. It's a thin chat UI over the RAG endpoint.

Q153. Is the frontend accessible (a11y)?
Minimally — it's a clean Tailwind UI but without deliberate ARIA labelling or keyboard-navigation testing, and monospace IDs may hurt readability. Accessibility would be a focused improvement: semantic landmarks, ARIA, focus management, and contrast checks.

Q154. How is the SPA served and how does deep-linking work?
It's built to static assets and served by nginx, which rewrites unknown paths to index.html so client-side routes deep-link correctly, and proxies /api to the gateway. index.html is sent no-cache so new deploys are picked up.

TIER 12 — Infrastructure, Docker & Kubernetes (moderately likely)

Q155. How is the system containerized and orchestrated?
Each service has a multi-stage Dockerfile; docker-compose runs the whole stack locally (4 Postgres, Kafka+Zookeeper, all services, gateway, frontend) with health checks and dependency ordering. For production there are Kubernetes manifests: Deployments, StatefulSets for the DBs and Kafka, Services, Ingress, ConfigMaps, Secrets, HPAs, NetworkPolicies, and PodDisruptionBudgets.

Q156. Explain your zero-downtime rollout strategy.
Deployments use RollingUpdate with maxUnavailable: 0 and maxSurge: 1, plus minReadySeconds: 10 and readiness probes — so a new pod must be ready before an old one is removed, keeping capacity up throughout. PDBs (minAvailable: 1) protect availability during voluntary disruptions like node drains.

Q157. How does autoscaling work and what's missing?
HPAs scale services on CPU (70–80% targets, 2→8/10 replicas). What's missing is memory-based or custom-metric scaling — the AI service is memory-bound and Kafka-consumer lag would be a better scaling signal for the ledger than CPU. CPU-only is a simplification.

Q158. What do your NetworkPolicies enforce?
Only backend-tier pods may reach Postgres (5432) and Kafka (9092); the frontend and gateway are walled off from the databases. That's good ingress segmentation. The gap is no egress policy — a compromised pod could call out anywhere — and no inter-service ingress restriction, which I'd tighten.

Q159. Your secrets are in YAML in the repo. How should this be done?
The committed secrets are placeholders, but committing secret manifests at all is bad practice. Production should use sealed-secrets, external-secrets backed by Vault/cloud secret managers, or SOPS-encrypted files — with rotation and RBAC on secret access — so plaintext secrets never live in git.

Q160. Your databases and Kafka are single-replica. Is that production-ready?
No — single-replica Postgres and a single Kafka broker are availability and durability risks (pod loss = downtime, and Kafka with replication-factor 1 can lose events). Production needs replicated Postgres (streaming replication/HA operator) with automated backups/PITR, and a 3-broker Kafka with min.insync.replicas=2. For the demo, single instances kept it simple.

Q161. The frontend has no PodDisruptionBudget. What's the impact?
During a node drain both frontend replicas could be evicted at once, briefly taking the UI down. It's a one-line fix — add a PDB with minAvailable: 1 — and I'd include it.

Q162. Containers run as root with no security context. Why does that matter?
Running as root widens the blast radius of a container escape. I'd add runAsNonRoot, a non-zero runAsUser, a read-only root filesystem, and dropped Linux capabilities. It's standard hardening that's currently absent.

Q163. How does the gateway cope with pods restarting and changing IPs?
nginx is configured with a dynamic resolver (resolver 127.0.0.11 valid=5s) and proxies via variables, so it re-resolves the service DNS name regularly instead of caching a stale pod IP at startup. That keeps routing correct across rollouts.

Q164. There's no observability stack. How would you monitor this in production?
Correct — there's no metrics/tracing/log aggregation yet. I'd add Prometheus + Grafana for metrics (request rates, latency, Kafka lag, HPA signals), OpenTelemetry tracing to follow a request across services and the event flow, and centralized logs (Loki/ELK) with correlation IDs, plus Alertmanager. For a distributed system this is essential, not optional.

Q165. How do you deploy to multiple environments (dev/staging/prod)?
Currently the manifests hardcode values, so multi-env would mean duplicating ConfigMaps — a weakness. I'd template with Helm or Kustomize so one chart parameterizes per environment, and wire it into a CI/CD pipeline that builds images, runs the test+coverage gate, and promotes through environments.

Q166. Why both a Pub/Sub emulator and Kafka in compose?
The architecture was designed transport-agnostic (the README references Google Cloud Pub/Sub as the target on GCP), so the emulator is there for that path, while Kafka is the primary local bus. The publisher/consumer abstraction means the messaging backend can change without touching domain code.

TIER 13 — Trade-offs, weaknesses & "what would you do differently" (common closers)

Q167. What's the single biggest weakness in your system?
Security around credentials and tenant trust: Base64 "hashing", hand-rolled JWT with a hardcoded secret fallback, and tenant scoping that trusts a client header rather than the JWT. Any one is serious for a finance app. They're also all well-understood, low-effort fixes, which is how I'd frame it — known, bounded, and remediable.

Q168. What's the biggest correctness weakness, separate from security?
VAT not being posted to the ledger, and money on floats with no enforced debit=credit invariant. Together they mean the books are net-only and not provably balanced at post time. Fixing the posting to include VAT lines, switching to decimals, and adding a balance assertion would make the ledger tax-correct and self-checking.

Q169. If you rebuilt this from scratch, what would you change architecturally?
I'd start as a modular monolith and only extract services where scaling/ownership truly demanded it; bind tenant to the JWT and add Postgres RLS from day one; use decimals and a proper JWT/hash library from the start; wrap outbox writes in the domain transaction; and stand up observability early. Most of the weaknesses come from breadth-over-depth under time pressure, not wrong direction.

Q170. Did microservices make this harder than it needed to be?
Yes, operationally — four databases, a broker, eventual consistency, and idempotency are a lot of moving parts for the user base. But it forced the interesting engineering (outbox, saga, RAG) the project set out to demonstrate, and the bounded contexts are real. The honest position: it's the right complexity for the learning goals, more than the business needs.

Q171. Where could a single failure cause data loss or corruption today?
A Kafka broker loss (replication factor 1) could drop in-flight events; a missing saga timeout can wedge a bill in REVERSING; concurrent posts/issues can double-count or oversell; and the in-memory audit/registration data vanishes on restart. None is unfixable, but each is a real failure mode I can name precisely.

Q172. How does the system behave under partial failure — say the ledger is down?
Operations keeps accepting and committing bills; their events queue in the outbox and retry with backoff until the ledger returns, at which point they're applied idempotently. So the write path stays available and self-heals. The user sees POSTED immediately; ledger reflection is delayed — acceptable eventual consistency.

Q173. How would you scale this to thousands of tenants and high volume?
Partition Kafka by tenant for parallel consumption; move ledger reads from the in-memory array to SQL aggregation (or materialized views) so instances scale horizontally; add read replicas and connection pooling; consider per-large-tenant DB routing; cache the compliance bundle; and batch/queue embeddings. The app already keys everything by tenant, which makes most of this incremental.

Q174. What's your disaster-recovery story?
Currently thin — no automated backups in the manifests. I'd add scheduled Postgres backups with point-in-time recovery to object storage, Kafka replication, infrastructure-as-code so the cluster is reproducible, and documented RTO/RPO targets with periodic restore drills.

Q175. How do you ensure the AI's financial answers are trustworthy enough to act on?
I'd be candid that they're decision-support, not authoritative — the authoritative numbers are the ledger reports. RAG grounding, low temperature, and source citation reduce error, and I'd add validation of any figures/codes the model emits against the ledger before display, plus a clear UI disclaimer. The model assists interpretation; it never replaces the books.

Q176. What did you learn building this?
That the hard part of microservices is data consistency, not the code split — outbox, idempotency, and sagas exist precisely because you gave up ACID. And that "make it work" and "make it secure/correct" are very different bars: the demo works, but a finance system's real bar is provable correctness and credential security, which is where my remaining gaps are.

TIER 14 — Deeper / specific code questions (less likely but possible)

Q177. Why is BillStatus.Reversing a distinct state rather than a boolean flag?
Because it's a genuine lifecycle state with its own legal transitions — from REVERSING you can only go to REVERTED (confirm) or back to POSTED (compensate), and you must reject normal mutations while a reversal is in flight. A dedicated enum state makes the state machine explicit and lets ensureMutable() block edits during the saga.

Q178. What does ensureMutable() protect against?
It throws if a bill is POSTED, REVERSING, or REVERTED when a mutation is attempted, enforcing that posted/finalized bills are immutable and that you can't edit one mid-reversal. It centralizes the "is this change legal right now" guard.

Q179. In the ledger, how is the original entry found for a reversal, and what if there are duplicates?
It searches for the tenant's entry with the matching reference, kind ORIGINAL, and no reversedBy set — i.e. the one unreversed original. If somehow two unreversed originals existed for a reference, it would pick the first; that's why the original-posting path should ensure one ORIGINAL per reference and why reversedBy guards against double-reversal.

Q180. Why does the AI ingest use deltaExpenses rather than recomputing from scratch?
The ledger sends the incremental expense delta per journal event so the AI can maintain a running total cheaply (O(1) per event) instead of re-reading the whole ledger. The trade-off is that a missed event corrupts the running total until a replay — which is why replayability matters.

Q181. Why is the expense-spike insight threshold hardcoded at €10,000?
It's a simple demonstrative rule, not a tuned model. It should be configurable per tenant (a small business and a large one have very different "spike" levels) or, better, statistical — flag deviations from the tenant's own historical baseline rather than an absolute number.

Q182. The AI keeps an ai_financial_events table that the RAG path doesn't query. Is that redundant?
Somewhat — events are stored both there and as RAG chunks, so there's duplication. The table is a durable event log/read model while the chunks serve semantic search; they serve different access patterns but I could unify them or drop the unused one to reduce redundancy.

Q183. How are provider order dependencies handled in the AI module, and is relying on declaration order safe?
The module comments note that the vector store must initialize before the seeder, and both before the AI service's init runs the seed. Relying on provider declaration order for lifecycle is fragile — Nest guarantees DI resolution order, not arbitrary init ordering across unrelated providers. The robust approach is explicit dependencies (inject and await) or lifecycle hooks that don't assume order.

Q184. Why suffix payment journal references with -PAYMENT?
To distinguish the payment entry from the original posting under the same business reference, so a bill's "post" and "pay" journals are separate, queryable entries and so their idempotency keys don't collide.

Q185. What does invoiceSent do in the ledger, and why nothing?
Nothing accounting-wise — it's logged as a commercial state change. Revenue is recognized at invoiceCreated (receivable/revenue), so "sent" is just a workflow transition (and the trigger for EDI delivery in Operations), not an accounting event. That avoids double-recognition.

Q186. In EDI import, why hardcode VAT-00-NO and account 665-09?
They're fallbacks so an imported bill is always valid even when the EDI payload lacks tax/account detail. The downside is lossy conversion — the original VAT treatment and proper expense account are dropped — so the importing company may need to correct the bill. A better design carries tax/account metadata across the EDI boundary.

Q187. When company A reverses an invoice, does B's imported bill change?
No — the two documents are decoupled after the EDI copy. A's reversal doesn't propagate to B. In a fuller EDI protocol there'd be a cancellation message so B is notified and can reverse its imported bill, but that's not implemented.

Q188. Why is the activity log capped (ring buffer) instead of unbounded?
To bound memory in the in-memory implementation. It's a demo convenience; the real fix is to persist activities to the DB with pagination rather than keep a fixed window in RAM, after which the cap disappears.

Q189. The outbox flush takes 50 rows and is single-flight. Could it lag?
Yes — if delivery is slow, the single in-progress flush plus a 50-row batch every 1.5s bounds throughput, so a backlog could build. For higher volume I'd increase batch size, parallelize delivery, or run multiple dispatchers with row-level locking (SELECT … FOR UPDATE SKIP LOCKED) so they don't double-send.

Q190. How would multiple outbox dispatchers avoid sending the same row twice?
With SELECT … FOR UPDATE SKIP LOCKED so each dispatcher claims a disjoint set of rows, or a status transition to IN_PROGRESS guarded by an optimistic version. Currently there's effectively one dispatcher per instance with a boolean guard, which is fine single-instance but not for horizontal scale.

Q191. Why deterministic idempotencyKey generation in enrich() rather than random?
Because determinism is what makes dedup work — the same business event produced twice must yield the same key so the consumer recognizes the duplicate. A random key would defeat idempotency. The random part is the separate eventId, used as the unique storage anchor.

Q192. How do you handle daylight saving / timezones in dates?
Dates are handled as date-only strings (YYYY-MM-DD) in many places and quarter boundaries are computed in UTC, which sidesteps most DST issues but can misattribute a transaction near midnight across timezones. For a single-country (Kosovo, one timezone) deployment it's adequate; multi-region would need explicit timezone handling.

Q193. Why are some interfaces (e.g. invoice events) missing the EventMeta idempotency fields?
Inconsistency in the build-out — bill events extend EventMeta (eventId/idempotencyKey) but some invoice/inventory events don't, so they rely on the in-memory dedup path rather than the DB markers. I'd normalize all events to carry metadata so every consumer can dedup uniformly.

Q194. The ledger's notifyAi falls back to a dynamic import('axios'). Why import lazily?
To avoid a hard dependency/load cost when Kafka is the active path — axios is only needed for the HTTP fallback, so it's imported on demand. It's a minor optimization; a static import would also be fine.

Q195. Why logLevel.NOTHING on the Kafka clients?
To silence kafkajs's verbose internal logging so it doesn't drown the application logs. In production I'd route Kafka logs into the structured logging pipeline at an appropriate level rather than mute them entirely, so broker issues are visible.

Q196. How are Kafka topics created?
The producers ensure the topic exists on startup via the admin client (creating it with 1 partition / replication-factor 1 if absent). That's convenient for dev but in production topics should be provisioned deliberately with proper partition counts and replication, not auto-created with single-replica defaults.

Q197. What ORM-level concurrency control do you have — optimistic locking?
None currently — there's no version column or optimistic-lock check, so last-write-wins and the concurrency races (double-post, oversell) are possible. Adding a TypeORM @VersionColumn and retrying on version conflict, or pessimistic row locks for the critical updates, is the fix.

Q198. How is the health of a service determined for k8s probes?
Each service exposes a health endpoint hit by readiness/liveness probes. They're shallow (process-up) rather than deep (checking DB/Kafka connectivity), so a service can report healthy while a dependency is down. Deeper readiness checks (verify DB and broker reachability) would make rollouts and routing safer.

Q199. Why is the global API prefix /api/v1 — do you have a versioning strategy?
The v1 prefix reserves room to evolve the API without breaking clients — a future v2 can run alongside. Beyond the prefix there's no formal deprecation policy yet; I'd add versioned contracts and a deprecation window when a breaking change is needed.

Q200. Walk me through exactly what happens if two users click "Post" on the same draft bill simultaneously.
Both requests load the DRAFT aggregate, both pass the "status is Draft" check, both set POSTED and save, and — critically — both could enqueue a billPosted event. The idempotency key (billPosted:tenant:Bill-id) saves the ledger from double-posting the journal, so the accounting stays correct, but two activity entries and a race on the write remain. A row lock or optimistic version on the bill is the clean fix; the idempotent consumer is the safety net that currently prevents the worst outcome.

TIER 15 — Conceptual / theory checks examiners use to test understanding

Q201. Define eventual consistency and where the user would notice it.
It means replicas/services converge to a consistent state after a delay, not instantly. A user would notice it as a brief lag between a bill showing POSTED in Operations and its journal entry appearing in the Ledger/reports — usually sub-second here, but unbounded if a service is down (the event waits in the outbox).

Q202. What is the CAP theorem and where does your system sit?
Under a network partition you can't have both consistency and availability. For the write path I chose availability + partition tolerance (AP) with eventual consistency — Operations keeps accepting bills even if the ledger is unreachable. Within a single service's database I still get strong consistency (CP-like) for that local transaction.

Q203. What is idempotency and why is it essential in event systems?
An operation is idempotent if doing it multiple times has the same effect as doing it once. It's essential because at-least-once delivery means consumers will sometimes see duplicates; idempotent processing (dedup keys, upserts, status guards) makes duplicates harmless, which is how you achieve correct results without exactly-once delivery.

Q204. Difference between orchestration and choreography in sagas?
Orchestration has a central coordinator that tells each service what to do next; choreography has services react to events and emit their own, with no central brain. Choreography is more decoupled but harder to reason about as steps grow; orchestration is easier to monitor/modify but adds a coordinator. I used choreography for the two-step storno.

Q205. What is the dual-write problem and how does the outbox solve it?
Dual-write is updating two systems (DB + broker) without a shared transaction, risking one succeeding and the other failing — leaving them inconsistent. The outbox writes the event into the same database as the state change, then a dispatcher publishes from there, so the event is never lost and the broker write is decoupled and retryable.

Q206. What does ACID mean and which parts do you give up across services?
Atomicity, Consistency, Isolation, Durability. Within one service's Postgres I keep all four. Across services I give up cross-service atomicity and isolation — there's no global transaction — and recover the needed guarantees with sagas, idempotency, and eventual consistency.

Q207. Why are JWTs called "stateless" and what's the cost?
Stateless because the server stores no session — the token itself carries the claims and is verified by signature, so any instance can authenticate a request without shared session storage. The cost is revocation: you can't easily invalidate a token before it expires, which is the refresh-token/blacklist discussion.

Q208. What is a value object and why immutable?
A value object is defined by its attributes, has no identity, and is interchangeable when equal (a BillLine, a Money). Immutability means it can be shared safely, can't be corrupted after construction, and forces "changes" to create new instances — which keeps the aggregate's invariants intact.

Q209. What is an anti-corruption layer and do you have one?
It's a translation layer that stops another system's model leaking into yours. The repositories' map-to/from-domain and the event DTOs act like one — the ledger's notion of a "journal entry" is built from Operations' event shape, not from Operations' internal model, so each context keeps its own language.

Q210. Explain cosine similarity in one breath and why it suits embeddings.
It measures the angle between two vectors, ignoring magnitude, so it compares direction/meaning rather than length. Text embeddings encode semantic meaning as direction in high-dimensional space, so two passages about the same topic have a small angle (high cosine), which is exactly what you want for "find related chunks".

Q211. What's the difference between authentication and authorization in your app?
Authentication is proving who you are — the JWT issued at login and verified by the guard. Authorization is what you're allowed to do — the RolesGuard hierarchy and (should-be) tenant scoping. The guard chain does authn first, then authz.

Q212. Why is double-entry "self-checking" and how does that help debugging?
Because every entry must balance, the sum of all debits must equal the sum of all credits across the whole ledger at all times. If they ever diverge, you have a provable bug — which is why the missing post-time balance assertion is worth adding: it turns a class of errors into an immediate, localized failure.

Q213. What is back-pressure and where would you apply it?
Back-pressure is signalling upstream to slow down when a consumer can't keep up. I'd apply it at the Kafka consumers (pause partitions when processing lags) and at the gateway (rate limiting), so a burst of bills doesn't overwhelm the ledger or the AI embedding calls.

Q214. What's the difference between horizontal and vertical scaling, and which does your design favour?
Vertical is a bigger machine; horizontal is more instances. The stateless services favour horizontal scaling (HPA adds replicas), which is the cloud-native default. The blockers to true horizontal scale are the in-memory ledger projection and single-instance assumptions, which I'd remove as discussed.

Q215. Why might you choose a modular monolith over microservices for a startup?
Lower operational cost, simple transactions (one DB, real ACID), easier debugging and deployment, and no eventual-consistency tax — while still keeping clean module boundaries so you can extract services later if scale demands. It's often the pragmatic first step; my src/ monolith embodies that option.

TIER 16 — "What if" and improvement questions (least likely, but good to have)

Q216. What if a tenant needs an immutable, tamper-evident audit trail for tax authorities?
I'd persist all events/journal entries append-only and add a hash chain — each record stores the hash of the previous plus its own content — so any later tampering breaks the chain and is detectable. Optionally anchor periodic digests externally. The append-only ledger is already half of this; the hashing makes it tamper-evident.

Q217. How would you implement GDPR "right to be forgotten" given an append-only ledger?
Financial records legally must be retained, so true deletion conflicts with tax law. The reconciliation is to keep the financial facts but pseudonymize/crypto-shred personal data: store personal data encrypted with a per-subject key and delete the key on erasure, and ensure descriptions never contain PII (which the compliance rules already push toward).

Q218. How would you add real-time notifications (e.g. "your invoice was paid")?
Since events already flow through Kafka, I'd add a notifications service that consumes the relevant events and pushes via WebSocket/SSE to the frontend (and email/SMS). The event-driven backbone makes this additive — no changes to existing services.

Q219. How would you support offline-first or intermittent connectivity for users?
Queue user actions client-side (IndexedDB) and sync when online, with idempotency keys on submissions so retries don't duplicate — the backend's idempotency already supports safe retries. Conflict handling would need optimistic concurrency on the server.

Q220. How would you A/B test or canary a new ledger version safely?
With a service mesh or weighted Kubernetes routing, send a small traffic slice (or a subset of tenants) to the new version, compare metrics/error rates, and roll forward or back. Because the ledger is idempotent and event-sourced from Kafka, a canary can even replay events to validate parity before taking live traffic.

Q221. How would you integrate with Kosovo's e-invoicing/fiscalization system if mandated?
Add an adapter in the EDI/operations boundary that formats invoices to the official schema and submits to the tax authority's API, storing the returned fiscal number on the invoice. The EDI inbox concept already models cross-party document exchange, so this is an additional outbound channel.

Q222. How would you handle a tax rule that depends on the counterparty's country (e.g. EU vs non-EU)?
Extend the tax category model with conditions (counterparty country, goods vs services) and evaluate them in the compliance validation engine, which would move from a fixed rule list toward a small rules engine. The reverse-charge categories are the first step toward this.

Q223. If the AI gave a wrong financial figure and a user acted on it, who's responsible — and how does your design limit that?
The authoritative source is always the ledger reports, and the AI is positioned as advisory with cited sources and a disclaimer; I'd also validate emitted figures against the ledger before display. Design-wise, never letting the AI write to the books (it's read-only) ensures it can't cause financial state changes, only inform.

Q224. How would you reduce LLM cost at scale?
Cache embeddings (already upserted, not recomputed), cache answers to common questions, use a smaller/cheaper model for routing and reserve the strong model for synthesis, batch embedding calls, and apply a relevance threshold so trivial queries skip the LLM and return the snapshot directly.

Q225. How would you test that tenant isolation truly holds?
A dedicated security test: seed data for tenants A and B, authenticate as A, and assert every endpoint (and the AI retrieval) returns only A's data even when B's ids/headers are supplied. I'd run it in CI so a regression that leaks across tenants fails the build. This directly targets the header-trust weakness.

Q226. What would break first if you onboarded a 10,000-employee enterprise instead of an SME?
The in-memory ledger projection (memory + multi-instance correctness), the single Kafka partition (throughput), the lack of period locking and approval workflows, and the weighted-average inventory at high transaction rates. Enterprises also expect SSO, granular permissions, and audit — all of which are beyond the current scope.

Q227. How would you add approval workflows (maker-checker) for large payments?
Introduce a pending-approval state in the relevant aggregate and a separate approve action gated by role, recording who approved. It fits the existing state-machine pattern — add states and transitions plus authorization checks — and emits events only after approval.

Q228. How would you migrate the in-memory audit log to persistent without downtime?
Add the DB-backed write path alongside the in-memory one (dual-write), backfill nothing (it was ephemeral anyway), then switch reads to the DB and remove the in-memory store. Because it's append-only and not on the critical financial path, the migration is low-risk.

Q229. Could you make storno synchronous to avoid the saga complexity?
Only by coupling Operations and Ledger in one transaction, which the database-per-service boundary forbids, or by a synchronous call that blocks Operations on Ledger availability and reintroduces the dual-write problem. The saga is the price of the decoupling; making it synchronous would trade resilience for simplicity.

Q230. If asked to remove Kafka entirely, what changes?
The publisher already has an HTTP fallback, so functionally it runs without Kafka — events POST directly to consumers. What I'd lose is durability, replay, consumer-group fan-out, and buffering during outages, so I'd need a persistent queue substitute. It proves the messaging layer is abstracted, but Kafka earns its place.

TIER 18 — Curveballs & pressure questions

Q246. "Your password hashing is wrong — did you not know better?"
I did — the code comment marks it explicitly as a demo placeholder with bcrypt/argon2 named as the production choice. I prioritized building the distributed-systems features the project is about and left a clearly-flagged stub for the credential store. It's a one-function change to argon2id with a salt, and I'd do it before any real deployment.

Q247. "Isn't most of the 'AI' just a wrapper around Gemini?"
The LLM call is one step; the engineering is the RAG pipeline around it — embedding, a pgvector store with an HNSW index, tenant-scoped retrieval, a seeded compliance corpus, grounded prompt construction, and a fallback path. Without that the model would hallucinate or leak across tenants. The value is the grounding and isolation, not the API call.

Q248. "If I delete one Kafka message, what breaks, and would you even notice?"
If it's an unprocessed business event, the corresponding journal/AI update never happens, and today you might not notice immediately because there's no reconciliation/alerting — that's a real observability gap. With replay (re-consume from offset) I can recover it, and I'd add a reconciliation check (e.g. Operations vs Ledger entry counts per tenant) to detect such drift.

Q249. "Prove your ledger can't silently go out of balance."
I can't prove it today, because there's no post-time assertion that debits equal credits — that's the gap. I can show every posting path constructs balanced pairs, and that getSummary() reports the global balance, but the guarantee should be enforced, not conventional. Adding the invariant check makes it provable and is my first ledger fix.

Q250. "Why should I trust an SME's books to an eventually-consistent system?"
Because the consistency window is small and bounded, the source of truth (each service's Postgres) is strongly consistent locally, and the design self-heals via outbox/idempotency rather than losing data. The user-visible guarantee is "your bill is safely recorded immediately; its ledger reflection follows within moments and is never lost." For batch-oriented accounting, that's appropriate — books are read in reports, not microseconds after entry.

Q251. "What stops me, as a logged-in user, from reading another company's ledger right now?"
Honestly, on the endpoints that trust x-tenant-id, the main barrier is that you'd have to supply another tenant's id and the UI won't — which is not real security. The fix I've identified is to derive tenant strictly from the verified JWT and add Postgres RLS, after which the database itself refuses cross-tenant reads. I'd call this the highest-priority hardening item.

Q252. "You list many weaknesses — does the system actually work?"
Yes — the full happy path works end-to-end: register, log in, create and post bills and invoices, run inventory, see balanced journals and reports, reverse via the saga, and query the AI. The weaknesses I'm naming are the difference between a working demo and a production-hardened financial product, and being able to enumerate them precisely is part of engineering maturity.

Q253. "Which one fix gives the most safety for the least effort?"
Binding tenant to the JWT (delete the header trust and the 'public' default) — a small change that closes the cross-tenant data-leak risk. Close behind: swapping Base64 for argon2 and adding the debit=credit assertion. All three are low-effort, high-impact.

Q254. "If your examiner were a CTO, why would they not deploy this tomorrow?"
Credential security (hashing/JWT/secrets), tenant-trust, no TLS, single-replica data stores with no backups, no observability, VAT not posted, and money on floats. None is architectural — they're hardening and correctness items — but collectively they're the gap between "demonstrates the architecture" and "handles real money safely."

Q255. "Defend keeping the in-memory ledger projection."
For a single instance at SME scale it makes reads instant and the code simple, and it's always backed by Postgres as the source of truth, so it's a cache, not the system of record. I'd defend it as a reasonable optimization for the current scale while acknowledging it must move to SQL aggregation the moment the ledger scales horizontally.

TIER 19 — Process, scope & reflection

Q256. How did you decide what was in scope versus out?
I anchored on the bounded contexts that make a finance tool useful (auth, compliance, operations, ledger) and added AI as the differentiator. I deliberately kept depth where correctness matters most (the event/saga flow, double-entry) and accepted stubs where it didn't change the architecture story (password hashing, in-memory audit). The scope was "demonstrate the architecture convincingly," not "ship to production."

Q257. How did you test the system manually during development?
Via docker-compose bringing up the whole stack with health checks, then exercising the API through the frontend and direct calls, watching events flow across services in the logs, and verifying journals balanced and reports rendered. The k6 script gave a basic load picture.

Q258. What was the hardest bug or design problem you hit?
Getting the storno saga and idempotency right — making reversal eventually consistent and safe under retries/duplicates without a distributed transaction, including the compensation path when the ledger can't find the original. It's the part where the distributed-systems theory had to become working code.

Q259. If a teammate joined tomorrow, how would they get productive?
The README documents the architecture, services, ports, event flow, and API; docker compose up brings everything up; and the DDD layering means a new feature follows the same domain/application/infrastructure pattern. TIER 20 — Final catch-all (least likely)

Q261. Why TypeScript over plain JavaScript for a financial system?
Static types catch a large class of errors at compile time (wrong shapes, null handling, enum misuse), which matters when money and state machines are involved, and they make the domain model self-documenting. NestJS is TypeScript-first, and the decorators that drive DI/validation rely on type metadata.

Q262. Why NestJS over Express or Fastify directly?
Nest gives structure out of the box — modules, dependency injection, guards, pipes, lifecycle hooks — which suits a layered DDD design across multiple services. Express alone would mean hand-rolling all of that. Nest still runs on Express underneath, so I keep the ecosystem.

Q263. Why Vite over Create React App?
Vite is faster (native ESM dev server, esbuild/SWC transforms), better maintained, and produces smaller optimized builds. CRA is effectively deprecated. For a modern React SPA it's the default choice.

Q264. Why Tailwind over a component library?
Utility-first CSS gave fine control over a custom Kosovo-branded design without fighting a component library's opinions, and the design tokens live in one config. The trade-off is verbose class lists and that I hand-built components a library would provide; for a bespoke look it was the right call.

Q265. Why store dates as strings rather than timestamps in some entities?
Accounting works in calendar dates (date of issue, due date, posting date), not instants, so date-only strings (YYYY-MM-DD) avoid spurious time/timezone components and match how reports group by day/quarter. Where true timestamps matter (createdAt), I use timestamptz.

Q266. How big is the codebase and how is it organized?
Roughly a hundred-plus TypeScript files split across the monolith reference (src/), the five deployable services (services/), the React frontend, the test suite, k8s manifests, and scripts. Each service mirrors the same domain/application/infrastructure layout for consistency.

Q267. What licensing and third-party considerations apply?
The project is MIT-licensed. Key third parties are NestJS, TypeORM, kafkajs, pgvector, React/Vite/Tailwind, and Google Gemini — the last being a paid external API with data-processing implications (Q116) that a production deployment must contract for.

Q268. How would you internationalize beyond Albanian and English?
Move from inline tr(en, sq) strings to a key-based i18n library with per-locale JSON files, externalize the compliance translations into the same system, and ensure date/number/currency formatting is locale-aware. The architecture already threads an x-lang header through to compliance, so the backend is partly ready.

Q269. What metrics would you put on a dashboard for the business, not just ops?
Per-tenant: active users, documents posted, total payables/receivables, overdue invoices, inventory value, and AI query volume. Ops-wise: event lag, error rates, p95 latency. The ledger and event streams already contain the raw data to derive these.

Q270. If this became a real company, what's the 6-month engineering roadmap?
Month 1–2: security hardening (hashing, JWT library, JWT-bound tenancy + RLS, TLS, secrets management) and the VAT/decimal correctness fixes. Month 3–4: HA data stores with backups, observability, saga timeouts, and concurrency controls. Month 5–6: e-invoicing/fiscalization integration, approval workflows, richer reporting, and a hardened multi-environment CI/CD. Throughout: grow the test suite, especially security and concurrency tests.
